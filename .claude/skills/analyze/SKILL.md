# 分析开发者模式录像

录制、上传、数据格式和报告各项的含义见 `docs/devmode.md`。这里只写分析的步骤。

## 参数

`$ARGUMENTS` 可以为空（分析最新一次上传），里面可能有：
- **上传编号**（`20261113-053518-c894f9`），可以只给末尾几位（`c894f9`），用 `--list` 找全名。
- **`列表`**：只跑 `--list`，列出所有上传，问负责人看哪个。
- **时刻**（`12.5`、`12秒`、`1分05`）：换算成秒，传给 `--at`（多个用逗号分隔）。
- **哪里不对**（`换弹的时候手闪一下`、`开镜卡`）：这是分析的重点，带着这个问题去看报告和图。

例子：`/analyze`、`/analyze c894f9`、`/analyze c894f9 12.5 换弹手闪一下`、`/analyze 列表`。

## 步骤

1. 找到编号。`node tools/devlog/analyze.mjs --list` 列出所有上传（编号、版本、模式、时长、帧率、标记数、视频片数）。
   - 上传的是地图（列表里显示"地图「…」"）：这不归本命令管，改用 `/map <编号>`。
   - 编号找不到：先列出最近几条，问负责人是哪个，不要猜。
2. 跑分析：

   ```bash
   node tools/devlog/analyze.mjs <编号> [--at 12.5,30] [--around 2]
   ```

   负责人说了时刻就加 `--at`；只想看帧率、没录画面或赶时间时加 `--no-video`。
   输出在 `tools/out/devlog/<编号>/`。
3. 读 `report.md`，再按需要看图（Read 工具能直接看 png、jpg）：
   - 一定看 `overview.png`（整段帧间隔，橙色竖线是 F8 标记）。
   - 有 F8 标记：每个标记都看 `marker-N.png`，录了画面就看 `marker-N-video.jpg`（标记前后每 0.1 秒一张，橙框是按键那一刻）。
     负责人按 F8 的时刻就是负责人觉得不对的地方，**这是最重要的线索**。
   - 负责人说的问题跟枪、手的动作有关：看 `jump-N.png`。
   - 加了 `--at`：看 `at-T.png`。
4. 带着负责人说的问题判断原因，读法见 `docs/devmode.md` 的"读报告的要点"：
   - 帧间隔中位数大约等于显示器刷新率。在高刷新率显示器上才出现的问题，要按那个帧率去想。
   - 卡顿时 CPU 时间小、帧间隔大：卡在显卡或浏览器合成。CPU 时间大：卡在脚本，看"在做什么"和附近事件。
   - 枪模跳变如果出现在本该连续的动作里（切枪、换弹），玩起来就是"闪一下"。
     开局 `lock`、死亡和重生前后的跳变是正常的（视角重置）。
   - 录像的版本比现在的 `main` 旧时，先 `git log` 看那之后相关代码改过没有，可能已经修了。
5. 需要定位到代码时再去读代码（`js/` 里对应的模块），把结论落到具体的文件和数值上（多半在 `js/config.js`）。

## 汇报

用大白话讲，先说结论，不要把报告整段贴给负责人：
- 一两句总体情况：显示器大概多少 Hz，整体流畅不流畅，卡顿多不多。
- 针对负责人说的问题（或者每个 F8 标记）：那一刻发生了什么，原因是什么，有多确定。
  关键的图用完整路径给出来，方便负责人自己打开看。
- 建议下一步：改什么（文件或参数）、要不要再录一次（录的时候开"录制画面"、出问题时按 F8）。
  **只给建议，不动手改代码**。负责人要修就开 issue 或说"做 N"，按 `/issue` 走。

## 注意

- 这是负责人真机上的数据，帧率和手感都可信。这台开发机的帧率不可信，不要拿开发机跑出来的数字和它比。
- **录下的数据和图都不往 GitHub 贴**（仓库是公开的）。issue 里只写结论和上传编号。
- 原始数据在 `~/direct-strike-data/devlogs/<编号>/`，只读不改，不删。
