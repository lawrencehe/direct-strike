# v0.26：项目管理迁到 GitHub（Issue、PR、Milestone、Release）

- **状态**：已上线（v0.26，2026-11-10）
- **分支**：`v0.26-github-workflow`
- **Issue**：#27　**PR**：#28
- **开始**：2026-11-10　**完成**：2026-11-10

## 需求

负责人原话（2026-11-10）：

> 对于我们项目的进展，我想通过 GitHub 把它管理起来，而不仅仅是记录代码。比如，我接入 PR 和 issue 能力，
> 把每一个问题/需求以及对应的功能开发进展、遗留问题全部记录起来。

之后确认："仓库和 GitHub 的边界，我赞同，可以直接按照新规则执行"；以前的资料也在 GitHub 上补。

## 范围

- 做：标签、Milestone、Issue、Release 的用法和边界；补建历史；`status.md` 的待办和已知问题改成 Issue；
  `ship.sh` 改成建 PR 在 GitHub 上合并、上线后建 Release；同步 CLAUDE.md 和文档。
- 不做：GitHub Actions、分支保护、PR 审核（一个人开发，PR 只用来留记录）；Projects 看板（issue 数量还少，需要时再加）。

## 方案和决定

**边界：会变的、要跟进的放 GitHub；为什么这样做留在仓库里。** CLAUDE.md 要求"拉下仓库就能接手"，而 issue 不在 git clone 里，
所以方案和决定仍写 `docs/requirements/`，issue 只管进度和讨论。表格见 `../workflow.md` 的"GitHub 上管什么"。

- 标签只加四个：`需求`、`bug`（沿用 GitHub 默认的，改了中文说明）、`待确认`、`想法`。默认的其他标签没删。
- 一个版本一个 Milestone，名字就是 `vX.Y`；`ship.sh` 建 PR 时自动挂上同名 Milestone，上线后 issue 都关了就关掉它。
- PR 用合并提交（`gh pr merge --merge`），不 squash：保留分支上的提交，和以前本地 `git merge` 的历史一致。不删分支。
- 仓库是公开的：GitHub 上不贴开发者模式录的数据、密码和令牌、玩家信息。
- **补建历史**（2026-11-10）：
  - v0.20 ~ v0.25 每个版本一个已关闭的 Milestone（截止日是上线日期）和一条已关闭的需求 issue（#1 ~ #5），正文取自需求文档。
  - v0.1 ~ v0.26 每个版本一个 Release，说明取自提交信息；v0.3、v0.4 原来没有 tag，补打在 05e9e47、eb54a26。
  - 旧版本补不了 PR（分支都已并入 main，没有差异）。
  - `status.md` 里的待办、已知问题和各需求文档"遗留"里还没做的，开成 #7 ~ #25；v0.26 键盘全屏的需求是 #6，真机确认 #26。
- **中途发生的事**：本需求进行时，另一个会话在同一个工作区用旧的 `ship.sh` 把键盘全屏发成了 v0.26（3cfa706，本地合并，没走 PR）。
  所以 #6 是手动关的，v0.26 的 Release 也是手动建的；本需求只改工具和文档，沿用 v0.26，不另起版本号、不打新 tag，走 PR #28 合并。
  教训：同一个工作区里多个会话同时做事，`ship.sh` 的 `git add -A` 会把别人的改动一起提交（v0.23 也出过一次）。

## 改动

| 文件 | 改了什么 |
|---|---|
| `tools/ship.sh` | 在分支上时推送分支 → 建 PR（`-c` 写 `Closes #N`，挂同名 Milestone，已有 PR 就沿用）→ `gh pr merge --merge` → 拉回 main；`--tag` 时建 Release、关 Milestone；`--no-pr` 走老的本地合并 |
| `.claude/skills/ship/SKILL.md` | 跟着改 |
| `CLAUDE.md` | 文档索引加 GitHub Issues；分支约定改成 PR；"需求文档和项目状态"各步加 issue |
| `docs/workflow.md` | 新增"GitHub 上管什么"（边界、标签、规则）；分支、版本号、每次改动的步骤 |
| `docs/status.md` | 待办和已知问题改成按标签筛选的 issue 链接；进行中看 Milestone 和 PR |
| `docs/requirements/README.md`、`_template.md` | 先有 issue；模板加 Issue / PR 一行，遗留开成 issue |
| `docs/decisions.md`、`docs/tools.md`、`docs/README.md` | 记录决定；工具表加 `gh` |

## 验证

- `gh` 权限：Issues、Pull requests、Contents 都能写（用不留痕迹的请求探过：改成原值、故意给不存在的分支 / 提交，看返回 422 而不是 403）。
- `ship.sh`：`bash -n` 通过；Milestone 查询、PR 正文拼接用真实接口单独试过。本 PR #28 就是用新的 `ship.sh` 建和合并的。

## 遗留

- 同一工作区多个会话同时开发会互相带走改动：以后并行做需求用 `git worktree`（v0.25 就是这样做的），不在同一个目录里同时改。
- 以后需要时可以加 GitHub Projects 看板、issue 模板。
