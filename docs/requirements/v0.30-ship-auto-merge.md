# v0.30（工具）：上线前自动把 main 合进分支，版本登记冲突自动解决

- **状态**：已上线（v0.30，2026-11-11）
- **分支**：`v0.30-ship-auto-merge`
- **Issue**：#47　**PR**：#49
- **开始**：2026-11-11　**完成**：2026-11-11

## 需求

来源：#37 上线过程中发现。几个 PR 从同一个旧 `main` 开出来，前一个上线后，后面的在 `README.md`、`index.html`、`docs/status.md`、
`docs/requirements/README.md` 和 `main` 冲突，`gh pr merge` 失败，自动上线失败（#11 第一次、#42 都是这样）。
负责人 2026-11-11："现在还遗留什么问题，都一并处理掉"。

## 范围

- 做：`ship.sh` 合并 PR 前先把 `origin/main` 合进分支，只有版本登记冲突时自动解决；版本号比 `main` 旧的拦下。
- 不做：代码、资源的冲突不自动解决（要人判断）；不自动改版本号。

## 方案和决定

- 冲突只在四个登记文件时：`README.md`、`index.html`、`docs/status.md` 用 `git merge-file --ours`（只在冲突段取分支的，不冲突的段照常合并），
  `docs/requirements/README.md` 用 `--union`（两边的行都留，分支的在上，正好是"新的在最上面"）。提交 `vX.Y：合并 main，自动解决…`。
- 别的文件冲突：`git merge --abort`，退出，列出文件。自动任务里就是 `上线失败` + 评论。
- 分支版本号比 `main` 旧（比如 v0.32 先上了再上 v0.31）：直接退出，不合并。版本号相同的工具类改动（比如本需求）照常放行。
- 合并后有非文档改动就再跑一次 verify，没过不推送。
- 只在走 PR（默认）时做；`--no-pr` 本地合并沿用原来的做法。
