## 需求

负责人原话（2026-11-11）：

> 每次做ISSUE，不管是你建立的还是我提的，都定一条规则：梳理文档放进项目中
> 不是说要把ISSUE直接复制到项目中，而是总结提炼做的内容，对相应的ISSUE建立索引，方便以后我们跟进/追踪/迭代项目

## 范围

- 做：定规则（手动会话和自动任务都要遵守）；新建 issue 索引；已有 issue 全部补登；已关闭的待确认把结论补回需求文档。
- 不做：不把 issue 原文搬进仓库；不改游戏。

## 方案和决定

- 原来只有"需求"类 issue 有需求文档，待确认的真机结果、bug 的处理结论、负责人在评论里拍板的规则都只在 GitHub 评论里，仓库里查不到。
- 新建 `docs/issues.md`：每条 issue 一行，列"提炼"（定了什么、做成了什么）、"现状"、"落地"（文档、版本、PR）。分"开着的"和"已关闭"两张表，新的在上面。
  需求文档仍然是需求的主文档；索引只做提炼和导航，不重复细节。
- 负责人补充（2026-11-11）："并不是说一个ISSUE就机械地建立一份文档或者一个独立的模块……要考虑到把ISSUE对应的内容，整理后融入到既有的项目文档中"。
  所以结论按主题融进已有文档：#15 #26 进 `ui.md` 的全屏规则和 `architecture.md` 的 Keyboard Lock 一条，#10 进已知的坑，#9 #12 进 `devmode.md`，
  #7 进 `config.js` 的 `economy` 注释，#35 的手臂模型问题变成 `art-sources.md` 里"挑人物模型要检查什么"。
  第一版曾在五份需求文档末尾追加"后续（issue 结论）"，太机械，撤掉了。
- 规则写进 `CLAUDE.md` 第 7 条（"需求文档和项目状态"）、`docs/workflow.md`、`docs/README.md` 的维护规则、自动任务的 `tools/autopilot/prompt.md`。
