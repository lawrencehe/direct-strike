## 需求

负责人（2026-11-10），接着 v0.26 把项目管理搬到 GitHub 之后：

> 以后的沟通模式，是不是不再完全依赖提示词，而是 GitHub 上建立 issue，提需求、提 BUG，然后给你编号，你就可以去解决。

讨论了几种全自动的做法（GitHub Actions 云端、self-hosted runner、开发机定时检查、云端定时任务）后，负责人选"开发机定时检查"，并要求：

> 得有个约定，有时候我只是想记录一些东西，并不是说马上让你进行开发。
> 如果要做的需求很多，可能导致一大堆的并行，会触发你的额度限制。我想还是一个时间一个任务最好。
> 你可以把任务的状态同步到评论区，我看到后觉得效果不错，还可以在上面提示你 commit push & deploy。
> 暂时不添加预览站点，因为这个项目还没有面客，没有实际用户使用。
> 30 分钟拉一次任务 issue，我不希望消耗 token。如果当前有任务已经在运行，那么 30 分钟拉到新任务，也不执行。

## 范围

- 做：标签约定、开发机上的定时调度、无人值守 Claude 的说明、评论区同步进度、评论触发上线；`ship.sh`、`deploy.sh` 能在 worktree 里跑。
- 不做：预览站点（负责人定的）；GitHub Actions；机器人账号（以后要推送通知再加）。

## 方案和决定

约定和用法写在 [../autopilot.md](../autopilot.md)，这里记为什么这样做。

- **开发机定时检查，不用 GitHub Actions**：工具链（Blender、verify 截图、deploy.sh）都在开发机上；self-hosted runner 在公开仓库上要防陌生人触发，红线多。
  定时检查不对外开任何口子。
- **开 issue 只是记录，打 `交给Claude` 才做**（负责人要求）。只认仓库主人打的标签：公开仓库里别人能开 issue 但不能打标签，脚本再查一遍打标签的人。
- **一次一个、检查不耗 token**（负责人要求）：`flock` 加锁，上一轮没结束这一轮直接退出；检查只用 `gh`（几秒），有任务才启动 Claude。
  另加每天最多 5 次、单任务 90 分钟超时、碰到额度限制歇 60 分钟——都是为了不把额度一次用光。
- **上线不启动 Claude**：负责人评论 `commit push & deploy` 后，脚本直接跑 `ship.sh -c N --tag`。上线是固定动作，不需要模型，也更可控。
  为此 develop 时 Claude 就把版本号、需求文档状态、`status.md` 写成上线后的样子（和 /ship 的约定一样），分支、PR、版本记在"待验收"评论末尾的注释里，脚本读它。
- **同一个 GitHub 账号**：Claude 用负责人的 token 发评论，评论第一行带 `<!-- autopilot -->` 来区分。代价是 GitHub 不推送"自己"的评论，负责人要看标签筛选；
  以后要通知就建机器人账号。
- **权限模式 `auto`**，不用 `bypassPermissions`：无人值守时危险操作会被拦下，拦下了任务就停在"等你回复"。
- **专用 worktree** `/home/donkey/direct-strike-autopilot`：v0.23、v0.26 都出过同一目录两个会话互相带走改动的事。上一轮残留的改动收进 stash，不删。
- **定时器跑 `origin/main` 上的脚本**：启动器每次从 `origin/main` 取脚本和提示词到固定目录（原子替换）再跑。
  直接跑工作目录里的不行：自动任务会在自己的 worktree 里切分支，手动会话也会切，bash 边读边执行，文件中途被换会出错；也保证跑的是合并过的版本。
- **部署要能从 worktree 跑**：`deploy/compose.yaml` 原来用相对路径挂 Caddyfile，从 worktree `docker compose up` 会把 fps-game 重建成挂 worktree 里的文件
  （worktree 一删配置就没了）。改成 `deploy.sh` 把 Caddyfile 原地复制到固定的 `/home/donkey/fps-conf/Caddyfile` 再挂。
  第一次部署时 fps-game 会因为挂载路径变了重建一次（一两秒，只影响本项目容器，relay 不动）。
- **`ship.sh` 能在 worktree 里跑**：`main` 只能在一个 worktree 检出，PR 合并后 `main` 被占着就用分离头指针切到 `origin/main` 部署；PR 模式不再推本地 `main`。
- 讨论过但没做：预览站点（负责人：项目还没面客）；Projects 看板；issue 模板（可以以后加）。

## 验证

- `bash -n` 三个脚本；`autopilot.sh --dry-run` 对真实仓库跑：没有任务时 3 秒结束、不启动 Claude。
- 打标签人、负责人回复、待验收注释的 jq 查询用真实 issue 数据试过。
- `claude -p --permission-mode auto --output-format json` 在开发机上能无人值守运行。
- 端到端（打标签 → 接手 → 待验收 → commit push & deploy → 上线）：本版本上线、定时器装好后，用一个小 issue 跑一遍，结果记在 #29。

## 遗留

- 无人值守的 Claude 没法把截图贴到 GitHub 评论。
- 几个 PR 同时待验收时要按版本号顺序上线，否则 `README.md` 冲突。

## 后续：`授权部署` 标签（#37，2026-11-10，沿用 v0.27 版本号）

负责人原话："目前的流程是我回复 commit push & deploy，我觉得这个方法有点低效，你可否设计一个状态，比如授权 claude 部署……你完成后，再把改变状态，并发表新的评论，关闭 issue。"

- 新标签 `授权部署`（只认负责人打的）。打在 `待验收` 上：下一轮直接上线。和 `交给Claude` 一起打：Claude 做到 `待验收` 后同一轮直接上线。
  有修改意见（`待验收` 里写了别的评论）时先改，改完再上线。评论 `commit push & deploy` 照样可用。
- 上线成功：去掉 `授权部署`、`Claude处理中`，评论"已上线"，issue 没被 PR 关掉就手动关。
  上线失败：回到 `待验收`、去掉 `授权部署`（不会每轮重试），评论原因。

  启动器变了，要重装一次定时器。
- 只改流程脚本和文档，游戏没变，所以不加版本号（不打新 tag）。
- **PR #38 提了没上线，整个机制卡死**（2026-11-11 发现）：定时器只跑 `main` 上的脚本，`授权部署` 在 #11、#39 上打了一晚上没人认；
